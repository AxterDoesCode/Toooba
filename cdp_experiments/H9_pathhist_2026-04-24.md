# H9 (H7 + D-style path-history signature) — negative finding

Date: 2026-04-24
Source: `src_Core/RISCY_OOO/coherence/src/prefetcher/CDPKillSwitchH9.bsv`
Logs: `builds/RV64ACDFIMSU_Toooba_bluesim/Logs/*.bin.log`

## Design (implemented)

H9 = H7 + 16-bit shift-XOR path signature.

```bsv
Reg#(Bit#(16)) pathSig <- mkConfigReg(0);

// In drainIncomingEvents on EvDemandLdMiss / EvDemandLdHit:
pathSig <= (pathSig << 4) ^ getPcHash(req);

// At every pcTable key site:
scanSig = getPcHash(req) ^ pathSig;
pctIdx = hash(scanSig);     // was hash(getPcHash(req))

// TT stores scanSig (not raw pcHash) in its pcHash field so Training-
// triggered lookups reach the same bucket as the original PrefetchIssue.
```

Everything else is H7 as-is: 4-bit counters, 3× useless amplification,
`us > uf` gate, overflow-bypass incomingQ, struct-refactored pendTlb,
decayInterval=256, matchBits=16, killThreshold=5.

## Two distinct failure modes

### 1. Training dilution → patricia collapse

Patricia under H7 has one dominant PC with 95.8% timely accuracy.
2,168 prefetches issued, 1,437 timely useful, 145k cycles saved at
DRAM. Under H9, each unique `(pcHash, path)` pair gets its own pcTable
entry. Patricia's single hot PC reaches via many different control-
flow paths (trie lookup walks are data-dependent), so its 2,168 training
events get scattered across ≥20 different signatures, each seeing too
few events to accumulate confidence ≥ `confidenceThreshold=1`.

Net: few or zero prefetches issued on patricia → back to NoPref2
performance. −12.06 pp of H7's win evaporates on this one bench, which
alone is worth ~−1.5 pp of geomean.

### 2. False-high confidence → health fabric DECERR

H7's single entry per PC averages offset confidences across all paths
that reach that PC. If one path visits a hot pointer at offset +3 and
another path at offset +6, H7 accumulates moderate confidence on both,
competing through decay. The "consensus" offset is what gets above
threshold.

H9 separates these into different entries. On health specifically, at
least one `(PC, path)` entry accumulated `conf=7` on an offset whose
"pointer" bit pattern in the cache line is *not* a real pointer — it
passes `matchBits=16` VPN-upper-bit filtering (health's pointer VPNs
dominate upper bits, so many word values look like pointers) and
translates via TLB to a valid PTE, but the resulting paddr is outside
mapped DRAM.

At cycle 1,200,222, such a prefetch reaches the LLC→AXI adapter, DRAM
returns DECERR (rresp=0x3), and the simulator halts. Toooba's
`LLC_AXI4_Adapter.rl_handle_read_rsp` explicitly exits on fabric
errors — there is no soft-error recovery.

H7 was safe because its single-entry-per-PC confidence averaging made
such conf=7 accumulations statistically unreachable: the bad-pointer
offset would have seen confidence cancellation from the many paths
where that bit pattern was NOT a pointer.

## What this tells us about path history

Path history works in the literature (SPP, VLDP, Pythia) because those
designs have:

- **Much larger tables** (SPP has 256-entry signature table + 512-entry
  pattern table, all BRAM; H9 reuses H7's 1024-entry pcTable)
- **Explicit signature compression** (SPP hashes signatures into
  modest-size buckets with explicit collision resolution)
- **Deeper lookahead** that amortizes per-signature training cost by
  chaining
- **Confidence aggregation across paths** via pattern-table sharing —
  not strictly per-signature keys

H9's "just XOR pathSig into pcTable key" is too naive. It's effectively
replacing 1024 PC buckets with 1024 random (PC, path) buckets, scattering
training with no compensating aggregation.

## Conclusion: H7 remains the dissertation reference

Path history, as implemented on the clean H7 pipeline, is *worse* than
the previous pre-H4 path-history result. The prior memory
(`cdp_insight_pathhist_order.md`) had D beating D2 by a small margin
but both net-negative — this re-baseline confirms path history is
still net-negative after the structural fixes.

The hypothesis that "path history would be better once back-pressure
was removed" is now falsified. H7's advantages are all back-pressure
and perms-tax; path keying is orthogonal to those and remains net-bad
on our pcTable sizing.

## What would be needed to rescue path history

Three paths forward, in rough order of effort:

1. **Aggressive signature compression.** Reduce pathSig entropy: use
   only 4 low bits, or XOR the pcHash with `(pathSig & 0x0F)` rather
   than full 16-bit XOR. Tradeoff: fewer distinct path contexts means
   less separation between paths but also less training dilution. An
   even more conservative "last PC only" version (XOR with single
   recent PC) may be worth a 30-minute try.

2. **Raise `confidenceThreshold` from 1 to 3.** Require more training
   per signature bucket before issuing. Would directly address dilution
   but at the cost of issuing fewer prefetches overall; might hurt
   patricia even more (since it trains fast on H7's confidenceThreshold=1).

3. **DRAM-safety filter.** Add a paddr-range check before issuing
   prefetch; drop prefetches whose translated paddr isn't in mapped
   DRAM. This is defensive infrastructure worth adding even to H7
   (though H7 doesn't surface the issue in the 8-bench suite). Would
   have prevented the health crash; would not by itself fix patricia.

4. **Proper SPP port.** Re-implement signature/pattern tables at the
   sizes SPP uses and measure. More than a 30-minute experiment.

## Status of prior path-history memory

`cdp_insight_pathhist_order.md` claimed "order-sensitive shift-XOR (D)
beats order-independent XOR (D2); recent PCs deserve more weight."
That specific claim was internal to the pre-H4 variant set and is not
overturned by H9. But the broader framing should be updated: path
history on the current pcTable sizing is **dominated** by H7 whether
shift-XOR'd, XOR'd, or not done at all. D vs D2 is an intra-dilution
comparison that doesn't matter for the dissertation.
