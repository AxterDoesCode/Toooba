# power-MID — CDP fires correctly at L1-overflowing size, working set still fits in LLC

Date: 2026-04-28
Config: CACHE_ALEX_SMALLISH (1MB LLC), power at MID_PROBLEM_SIZE
  (4×7×2×4 = 224 leaves, ~14KB working set — L1 (8KB) overflowed, LLC (1MB) not)
Logs:
  - `/local/scratch/ac2822/NewTooobaLogs/variantH7_power_mid224_2026-04-27/`
  - `/local/scratch/ac2822/NewTooobaLogs/variantNoPref_power_mid224_2026-04-28/`

## Goal

`power_smallint_2026-04-27.md` showed CDP firing with 85% useful rate but
zero DRAM-bypass at SMALL_INT (~9KB, barely overflows L1). MID was the
next size up that fits within the per-config wall-clock budget (~30 min)
to test whether L1-overflow alone produces a meaningful cycle delta.

## Sizing decisions

| config | leaves | work-set | wall-clock per config |
|:---|---:|---:|---:|
| TINY (4×4×2×2) | 64 | ~5KB | ~8 min |
| SMALL_INT (4×6×2×3) | 144 | ~9KB | ~17 min |
| **MID (4×7×2×4)** | **224** | **~14KB** | **~30 min ✓** |
| MEDIUM (6×8×3×4) | 576 | ~35KB | >45 min, killed |
| SMALL_PROBLEM_SIZE | 6,400 | ~800KB | >1.5 h, killed |

MID overflows L1 (~5KB more than L1's 8KB) but is still <2% of LLC.

## Results

| variant | cycles | instr | CPI | Δ vs NoPref |
|:---|---:|---:|---:|---:|
| NoPref-MID | 7,345,210 | 1,835,711 | 4.001 | reference |
| H7-MID | 7,344,718 | 1,835,711 | 4.001 | **−492, −0.0067%** |

Almost identical. Trend across the power sizing sweep is consistent:

| size | working set | NoPref cyc | H7 cyc | Δ | Δ% |
|:---|---:|---:|---:|---:|---:|
| TINY | ~5KB (fits L1) | 2,304,694 | 2,304,674 | −20 | −0.0009% |
| SMALL_INT | ~9KB | 4,823,765 | 4,823,192 | −573 | −0.012% |
| MID | ~14KB | 7,345,210 | 7,344,718 | −492 | −0.0067% |

The cycle gain does NOT scale with workload size — it stays in the noise
at every size that fits in LLC.

Causal chain:
- 29 timely-useful prefetches  → 29 demand-miss reduction (4,725 → 4,696, exact match)
- demandMissLL identical (261 each) → CDP didn't change DRAM volume
- 29 LLC-hit prefetches × ~10 cyc each ≈ 290 cyc savings
- Observed cycle Δ = 492 — within range with owned/late merges

Useful rate: 41 / 41 = 100% (zero useless). CDP is firing perfectly on
content-directed pointer chase (Root → Lateral → Branch → Leaf).

## Why MID isn't bigger than SMALL_INT in cycle gain

SMALL_INT delivered −573 cyc; MID delivered only −492 cyc despite a
larger working set. MID's 41 useful (vs SMALL_INT's 29) is offset by:
- More prefetchHits as overhead (85 vs 90 — comparable)
- 12 lateUsefulPrefetch in MID vs SMALL_INT's 5 (more racing-behind-demand)

Net per-bench savings is masked by the 6.6M-cyc denominator.

## Verdict

Power's pointer-chase pattern is real but its working set tops out below
LLC at every wall-clock-feasible size. Three converging size points all
land in the noise floor:
- TINY: 0% (fits in L1)
- SMALL_INT: 0.012% (overflows L1 by ~1KB)
- MID: 0.0067% (overflows L1 by ~6KB)

To get a quantitative win, power needs either:
1. **TINYLL config** (LLC=128KB) — would push 14KB above 128KB? No, still well under. Working set would need ~1MB+ to bypass DRAM.
2. **MEDIUM build infrastructure fix** — `R_RISCV_HI20 relocation truncated` at MEDIUM is the existing blocker. Fixing it would enable 35KB working set and possibly larger.
3. **Quantitative claim is not extractable** at any feasible power size on this Toooba config.

## Where this leaves power for the dissertation

Power-MID is the **definitive qualitative validation** point:
- Full pointer-chase data structure
- 100% useful rate for CDP
- Zero pollution
- L1-overflowing working set

But the cycle delta is sub-noise. Frame as:
- "CDP fires correctly on pointer-chasing benchmarks beyond Olden,
  achieving 100% useful prefetch rate on power-MID. Quantitative cycle
  benefit requires DRAM-bypass material, which power's working set does
  not reach at any wall-clock-feasible size on this configuration."

Exclude power from the standing 8-bench iteration set and the geomean
table; keep MID logs as a clean validation data point.
